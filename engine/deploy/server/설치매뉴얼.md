# LogTriage 서버형 설치 매뉴얼 (Linux · 오픈소스 스택)

버전: 2026-09-10 / 대상: OS 만 설치된 Linux 서버에 **nginx(WEB) + Python 앱서버(WAS) + PostgreSQL 또는 SQLite(DBMS)** 구성으로 LogTriage 를 설치·운용하는 담당자

---

## 0. 한눈에 보기

| 구분 | 내용 |
|---|---|
| 구성 | 브라우저 → **nginx**(80/443, 업로드 700MB, 긴 응답 대기) → **logtriage-server**(Python, 127.0.0.1:8080, systemd) → **PostgreSQL**(logtriage DB) 또는 **SQLite**(단일 파일) |
| 설치 명령 | `sudo bash engine/deploy/server/install.sh` (인터넷 가능 서버) / 폐쇄망은 오프라인 번들 반입 후 같은 명령 |
| 소요 | 온라인 5~10분(패키지 내려받기 포함), 오프라인 3분 |
| 접속 | `http://<서버IP>/` (또는 `--tls` 시 `https://`) → 설치 끝에 표시된 비밀번호로 로그인 |
| 설정 파일 | `/etc/logtriage/server.env` (비밀번호·DB·포트·허용 경로) |
| 서비스 | `logtriage-server`, `nginx`, `postgresql` (systemd) |
| 데이터 | `/opt/logtriage/{data,uploads,reports,rules-local}` + DB |
| 갱신 | 룰팩(.rpk + .key) 업로드 — 웹 UI [룰팩 업데이트] |
| 앱서버 한계 | Python 표준 라이브러리 HTTP 서버(스레드)입니다. 반드시 nginx 뒤 루프백(127.0.0.1)에서만 운용하고, 동시 처리는 `LOGTRIAGE_MAX_ACTIVE`(기본 3)로 제한됩니다. 외부 직접 노출·대규모 동시 사용자 용도가 아닙니다 |

```
[사용자 PC 브라우저] ──HTTP/HTTPS──▶ [nginx :80/:443] ──▶ [logtriage-server :8080] ──▶ [PostgreSQL :5432 | SQLite 파일]
                                         WEB                     WAS(Python 3.10+)          DBMS
                                                                   ├ 로그 업로드 → uploads/
                                                                   ├ 분석 엔진(rules/errorcodes/manuals)
                                                                   └ 보고서 → reports/
```

## 1. 사전 요구사항

### 1.1 서버
| 항목 | 최소 | 권장 |
|---|---|---|
| OS | RHEL/Rocky/AlmaLinux/CentOS Stream **8 또는 9**, Ubuntu **20.04/22.04/24.04**, Debian **11/12** (x86_64) | Rocky 9 / Ubuntu 22.04 |
| CPU / 메모리 | 2 vCPU / 4 GB | 4 vCPU / 8 GB (600MB 로그 분석 시 피크 약 150MB, 동시 3건 여유) |
| 디스크 | 10 GB (`/opt`) | 50 GB 이상 — 업로드 로그(uploads/)와 보고서가 쌓임 |
| 파이썬 | 3.10 이상 (RHEL8 계열은 `python3.11` 패키지를 설치 스크립트가 자동 선택) | 3.11 |
| 권한 | root(sudo) | |
| 포트 | 80 (TLS 시 443) 인바운드 / 8080·5432 는 서버 내부만 | |

### 1.2 인터넷 여부에 따른 준비물
| 상황 | 준비물 |
|---|---|
| 서버가 인터넷(또는 사내 미러 저장소)에 연결됨 | 소스 번들 `logtriage-server-<날짜>.tar.gz` 만 |
| **폐쇄망** | (1) 소스 번들 (2) 번들 안의 `deploy/server/wheels/`(파이썬 패키지, 자동 포함) (3) **OS 패키지**: 폐쇄망 서버와 같은 배포판·버전의 인터넷 PC 에서 `fetch_os_packages.sh` 로 수집해 번들에 포함 |

> nginx·PostgreSQL 이 이미 서버에 설치돼 있으면 (3)은 필요 없습니다. 설치 스크립트가 있는 것은 그대로 씁니다.

### 1.3 반입 파일 만들기 (인터넷망 PC — Windows Git Bash 또는 Linux)
```bash
# (선택, 폐쇄망 서버에 nginx/postgresql/python3 가 없을 때) 폐쇄망 서버와 같은 OS 의 인터넷 Linux 에서
bash engine/deploy/server/fetch_os_packages.sh          # → engine/deploy/server/pkgs/<os><버전>/ 에 rpm/deb 수집

# 번들 생성 (어느 인터넷 PC 에서나)
bash engine/deploy/server/make_offline_bundle.sh         # → ../logtriage-server-YYYY.MM.DD.tar.gz  (소스 + Linux wheel + pkgs)
```
생성된 tar.gz 와 함께 **룰팩 키(rulepack.key)** 는 별도 매체로 반입합니다(zip 과 같은 경로에 두지 않음).

## 2. 설치 (5단계)

### 2.1 번들 풀기
```bash
mkdir -p /tmp/lt && cd /tmp/lt
tar xzf /path/to/logtriage-server-2026.09.10.tar.gz      # engine/ 폴더가 생김
```

### 2.2 설치 스크립트 실행
```bash
sudo bash engine/deploy/server/install.sh --allow-dir /var/log --allow-dir /data/logs
```
| 옵션 | 의미 | 기본 |
|---|---|---|
| `--db postgres` / `--db sqlite` | 저장소 선택 | PostgreSQL 설치 가능하면 PostgreSQL, 아니면 SQLite |
| `--tls` | 자체 서명 인증서로 443 활성화, 80→443 리다이렉트 | 없음(80 만) |
| (`--password` 없음) | 공용 비밀번호는 명령행으로 받지 않음(ps · 셸 기록 노출) — 주면 설치가 멈춤 | 무작위 12자를 `/etc/logtriage/server.env` 에만 기록(화면 · 설치 기록에 안 찍음) |
| `--port <n>` | 앱(WAS) 내부 포트 | 8080 |
| `--allow-dir <경로>` | 서버에 이미 있는 로그를 화면에서 바로 고를 수 있는 디렉터리(반복 가능) | /var/log |
| `--offline` | 인터넷을 쓰지 않음(번들에 `pkgs/<os>` 가 있으면 자동) | 자동 판단 |
| `--no-nginx` | nginx 없이 앱을 0.0.0.0:8080 에 직접 노출(테스트용) | nginx 사용 |
| `--no-firewall` | firewalld/ufw 포트 개방 생략 | 개방 |
| `--journal-access` | 서비스 계정에 adm/systemd-journal 그룹 부여(서버 전체 로그 읽기) | 미부여(ACL 권장) |

스크립트가 하는 일(순서): OS 판별 → 패키지 설치(nginx, postgresql, python3) → `/opt/logtriage` 에 앱 복사 → venv + PyYAML(+psycopg2) → 서비스 계정 `logtriage` → PostgreSQL initdb·DB/계정 생성(또는 SQLite) → `/etc/logtriage/server.env` 작성 → systemd 등록·기동 → nginx 설정·reload → 방화벽 개방 → 헬스체크 출력.
전체 로그는 `/var/log/logtriage-install.log` 에 남습니다.

### 2.3 설치 완료 화면 예
```

  웹 UI : http://10.0.0.21/
  비밀번호 : Kx7mQ2pLw9Rt      (변경: /etc/logtriage/server.env → systemctl restart logtriage-server)
  저장소   : PostgreSQL logtriage@127.0.0.1
  헬스체크 : {"ok": true, "version": "0.1.0", "db": {"kind": "postgresql", "incidents": 0}}
  서비스   : systemctl status logtriage-server nginx postgresql
```

### 2.4 접속 확인
1. PC 브라우저에서 `http://<서버IP>/` → 로그인 화면 → 위 비밀번호 입력.
2. 대시보드가 뜨면 [로그분석] → 로그 파일을 드래그(또는 [서버 경로]에서 `--allow-dir` 아래 파일 선택) → [즉시 분석 시작].
3. 분석 리포트가 보이면 설치 완료. `/healthz` 로 상태 확인:
```bash
curl -s http://127.0.0.1:8080/healthz      # 앱 직접
curl -s http://<서버IP>/healthz            # nginx 경유
```

### 2.5 룰팩(지식베이스) 적용
- 웹 UI [룰팩 업데이트] → `rulepack-YYYY.MM.DD.rpk` 선택 → `rulepack.key` 선택 → 적용. 서명이 맞지 않으면 거부됩니다.
- 명령줄: `sudo -u logtriage /opt/logtriage/venv/bin/python /opt/logtriage/tools/rulepack_cli.py apply --key-file /경로/rulepack.key /경로/rulepack-YYYY.MM.DD.rpk`
- 적용 후 화면 우상단 `룰 N · 코드 N` 숫자가 바뀌면 성공. 재기동 불필요.

## 3. 설정 (`/etc/logtriage/server.env`)

```ini
LOGTRIAGE_HOST=127.0.0.1                 # nginx 뒤 → 루프백. nginx 없이 쓰면 0.0.0.0
LOGTRIAGE_PORT=8080
LOGTRIAGE_PASSWORD=Kx7mQ2pLw9Rt          # 웹 접속 비밀번호(비우면 인증 없음 — 권장하지 않음)
LOGTRIAGE_DB=postgresql://logtriage:<pw>@127.0.0.1:5432/logtriage   # 또는 sqlite:////opt/logtriage/data/logtriage.db
LOGTRIAGE_ALLOW=--allow-dir /var/log --allow-dir /data/logs           # 서버 로컬 로그 허용 디렉터리
LOGTRIAGE_UPLOAD_KEEP_DAYS=14            # 업로드 원본 보존 일수(logtriage-cleanup.timer 가 매일 삭제)
LOGTRIAGE_MAX_ACTIVE=3                   # 동시 분석·업로드 상한(초과 시 즉시 거절)
```
변경 후: `sudo systemctl restart logtriage-server`
파일 권한은 `root:logtriage 640` — DB 비밀번호가 들어 있으므로 다른 계정에 열지 않습니다.

### 3.1 서버 로컬 로그를 직접 분석하려면
- `LOGTRIAGE_ALLOW` 에 디렉터리를 추가하고 재기동.
- 서비스 계정 `logtriage` 가 그 파일을 **읽을 수 있어야** 합니다. 기본 방식은 파일별 ACL(필요한 디렉터리만):
  `setfacl -R -m u:logtriage:rX /app/jeus/logs` (신규 파일까지 적용: `setfacl -R -d -m u:logtriage:rX /app/jeus/logs`)
- 서버 전체 시스템 로그(`/var/log`, journal)를 읽어야 하면 설치 시 `--journal-access` 로 `adm`/`systemd-journal` 그룹을 부여합니다(권한 범위가 넓으므로 필요할 때만).
- 서비스는 `ProtectHome=read-only` 로 동작하므로 `/home` 아래 로그는 읽기만 가능하고 `/root` 는 접근할 수 없습니다.

### 3.2 TLS(HTTPS)
- 설치 시 `--tls` 를 주면 `/etc/logtriage/tls/server.{crt,key}` 자체 서명 인증서(825일, SAN 에 호스트명·IP 포함)로 443 을 열고 80 은 443 으로 301 리다이렉트만 합니다(평문으로 로그인·업로드 처리 안 함).
- 자체 서명은 **초기 구축용**입니다. 브라우저가 신뢰하지 않으므로 운영은 기관 내부 CA(PKI) 인증서로 교체하십시오. 만료 확인: `openssl x509 -in /etc/logtriage/tls/server.crt -noout -enddate`
- 리다이렉트 확인: `curl -sI http://<서버IP>/ | head -1` → `301`, `curl -skI https://<서버IP>/login | head -1` → `200`.
- 사내 CA 인증서로 바꾸려면 같은 경로에 crt/key 를 덮어쓰고 `sudo systemctl reload nginx`.
- 나중에 TLS 를 켜려면 `sudo bash engine/deploy/server/install.sh --tls` 를 다시 실행(재설치 안전 — 비밀번호·DB 유지).

### 3.3 업로드 크기·시간
- 앱: 1파일 600MB 상한(`MAX_UPLOAD`). nginx: `client_max_body_size 700m`, `proxy_read_timeout 1800s`.
- 실측: 200MB 6파일 64초, 325MB(gz 포함) 72초, 1GB 단일 파일 617초 → 1GB 급은 장애 시각 전후 구간만 잘라 올리는 것을 권장.

## 4. 운영

### 4.1 서비스 관리
```bash
systemctl status  logtriage-server nginx postgresql
systemctl restart logtriage-server        # 설정 변경 후
journalctl -u logtriage-server -f         # 앱 로그(접속·분석 오류)
tail -f /var/log/nginx/logtriage_access.log /var/log/nginx/logtriage_error.log
```

### 4.2 디렉터리
| 경로 | 내용 | 정리 |
|---|---|---|
| `/opt/logtriage/uploads/` | 업로드된 로그 원본(재분석용, 개인정보 포함 가능) | `logtriage-cleanup.timer` 가 매일 `LOGTRIAGE_UPLOAD_KEEP_DAYS`(기본 14) 초과분 삭제. 실행 기록: `journalctl -u logtriage-cleanup` |
| `/opt/logtriage/reports/` | 생성 보고서(docx/html/hwpx) — 웹 `/reports/` 에서 내려받기 | 필요 시 정리 |
| `/opt/logtriage/data/logtriage.db` | SQLite 저장소(선택 시) | 백업 대상 |
| `/opt/logtriage/rules-local/` | 사이트 커스텀 룰(룰팩 갱신에 영향 없음) | 백업 대상 |
| `/opt/logtriage/rules, errorcodes, manuals` | 룰팩으로 갱신되는 지식베이스(직접 수정 금지) | |
| `/etc/logtriage/server.env` | 설정 | 백업 대상 |

### 4.3 저장소(DBMS) 내용
- `incidents` : 분석 이력(분석 결과 JSON 전체) — 최근 500건 보관, 화면은 최근 50건.
- `events` : 로그 검색용 이벤트 원본(분석 건당 최대 20만 건) — 최근 50건만 보관.
- 데스크톱 exe 에서 쓰던 `incidents.json` 을 `/opt/logtriage/` 에 두고 기동하면 DB 가 비어 있을 때 자동 이관됩니다.

### 4.4 명령줄(CLI)
```bash
logtriage /var/log/tomcat/catalina.out --product tomcat --incident-time "2026-09-02 14:05"
logtriage --incident-time "2026-09-02 14:05" --input /logs/catalina.out:tomcat:was01 --input /logs/alert_orcl.log:oracle:db01
```

### 4.5 사용자·인증
- 앱 비밀번호는 **공용 1개**(쿠키 세션, HttpOnly, 서버 재기동 시 세션 소멸)로 사용자별 식별·감사가 되지 않습니다 — 초기 구축·비상용으로 보고, 운영은 nginx 사용자별 인증 또는 사내 SSO(리버스 프록시 인증)를 기본으로 두십시오.
- nginx 사용자별 인증(auth_basic) 예:
```bash
sudo dnf install -y httpd-tools   # Debian: apt-get install -y apache2-utils
sudo htpasswd -c /etc/logtriage/htpasswd hong      # 사용자 추가(-c 는 최초 1회만)
# /etc/nginx/conf.d/logtriage.conf (Debian: sites-available/logtriage) 의 location / 에 추가:
#     auth_basic           "LogTriage";
#     auth_basic_user_file /etc/logtriage/htpasswd;
sudo nginx -t && sudo systemctl reload nginx
```
  접속 사용자는 nginx access 로그(`logtriage_access.log` 의 remote_user)로 추적합니다. 사용자 폐기는 `htpasswd -D`.
- 앱 포트(8080)와 DB 포트(5432)는 루프백에만 열려 있어 외부에서 직접 접근할 수 없습니다.

### 4.6 데이터 보존·삭제 정책(한눈에)
| 데이터 | 위치 | 보존 | 삭제 트리거 | 비고 |
|---|---|---|---|---|
| 업로드 로그 원본 | `uploads/` | `LOGTRIAGE_UPLOAD_KEEP_DAYS`(14일) | `logtriage-cleanup.timer` 매일 | 개인정보 포함 가능 — 가장 먼저 삭제 |
| 분석 이력(분석 결과 JSON) | DB `incidents` | 최근 500건 | 새 분석 건 저장 시 초과분 자동 삭제 | 마스킹된 메시지 일부 포함 |
| 로그 검색용 이벤트 원본 | DB `events` | 최근 50건 | 새 분석 건 저장 시 초과분 자동 삭제 | 분석 건당 최대 20만 건, 주민번호 마스킹 |
| 생성 보고서 | `reports/` | 무기한 | 수동(`find reports -mtime +N -delete`) | 반출 전 내용 검토 |
| 백업 | `backup/` | 30일 | `backup.sh` 실행 시 초과분 삭제 | DB 덤프 = 분석 이력·이벤트 사본. `--with-env` 사용 시 DB 비밀번호 포함 → 별도 보관 |
분석 건을 DB 에서 지워도 백업 만료(30일) 전까지는 백업 안에 남습니다. 즉시 파기가 필요하면 해당 백업 파일도 삭제하십시오.

## 5. 폐쇄망 설치 절차 요약

```
[인터넷망 Linux(같은 OS)]  fetch_os_packages.sh  ─┐
[인터넷망 PC]              make_offline_bundle.sh ─┴─▶ logtriage-server-<날짜>.tar.gz ──(매체 반입)──▶ [폐쇄망 서버]
                                                                                        tar xzf → sudo bash engine/deploy/server/install.sh
```
1. 인터넷망: (필요 시) OS 패키지 수집 → 번들 생성.
2. 반입 매체 검사 후 폐쇄망 서버로 복사.
3. `tar xzf` → `sudo bash engine/deploy/server/install.sh` (pkgs 가 있으면 자동으로 `--offline`).
4. 룰팩 키는 별도 경로로 반입해 [룰팩 업데이트]에서 사용.

오프라인 설치 시 검증 포인트: `install.sh` 출력의 `[OS] … 오프라인=1 pkgs=…`, `[3/8] … wheels/` 에서 설치되는지.

## 8. 문제 해결

| 증상 | 확인 | 조치 |
|---|---|---|
| 설치 중 `python3 — 3.10 이상 필요` | `python3 -V` | RHEL8: `dnf install python3.11 python3.11-pip` 후 재실행(스크립트가 자동 선택). Ubuntu 20.04: deadsnakes 또는 3.10 패키지 |
| `[3/8] wheels/ 에서 설치 실패` | 번들 `deploy/server/wheels/` 에 서버 파이썬 버전용 `*cp3XX*manylinux*.whl` 이 있는지 | 인터넷망에서 `make_offline_bundle.sh` 재생성(3.9~3.13 wheel 포함) |
| 앱 서비스 기동 실패 | `journalctl -u logtriage-server -n 50` | `server.env` 의 DB URL·비밀번호 확인, `sudo -u logtriage /opt/logtriage/venv/bin/python -m logtriage.server --base /opt/logtriage --port 8080` 로 직접 실행해 오류 확인 |
| `lxml` 없음 오류(보고서 생성 실패) | 구버전 번들로 설치 | 새 번들로 `install.sh` 재실행(wheels 에 lxml 포함) |
| `psycopg2` 없음 오류 | PostgreSQL 선택했는데 wheel 없음 | `--db sqlite` 로 재설치하거나 wheels 에 psycopg2-binary 추가 |
| PostgreSQL 접속 거부 | `sudo -u postgres psql -c '\l'` | `systemctl start postgresql`; RHEL 은 `postgresql-setup --initdb` 가 됐는지 `/var/lib/pgsql/data/PG_VERSION` 확인; Debian 은 `pg_lsclusters` |
| `logtriage` 로그인 실패(password authentication failed / no pg_hba.conf entry) | `sudo -u postgres psql -qtAc 'show hba_file'` 의 파일 | `host logtriage logtriage 127.0.0.1/32 scram-sha-256` 줄이 ident/peer 규칙보다 앞에 있는지 확인 후 `SELECT pg_reload_conf();` |
| 분석 요청이 "동시 분석 한도 초과" 로 거절 | 진행 중 분석 수 | 끝난 뒤 재시도. 상한 조정: `LOGTRIAGE_MAX_ACTIVE` (메모리 여유 확인 후) |
| 브라우저 502 Bad Gateway | nginx 는 떠 있고 앱이 죽음 | `systemctl restart logtriage-server`; RHEL 에서 SELinux `setsebool -P httpd_can_network_connect 1` |
| 브라우저 413 Request Entity Too Large | 700MB 초과 업로드 | 로그를 장애 전후 구간으로 잘라 올림(앱 상한 600MB) |
| 업로드 중 504 / 응답 없음 | 대용량 분석(1GB 급 10분 이상) | 정상 대기(nginx 1800s). 더 크면 파일 분할 |
| 방화벽 때문에 접속 불가 | `firewall-cmd --list-all` / `ufw status` | `--no-firewall` 로 설치했으면 수동 개방: `firewall-cmd --permanent --add-service=http && firewall-cmd --reload` |
| 서버 경로 선택에 파일이 안 보임 | `LOGTRIAGE_ALLOW` 와 파일 읽기 권한 | 3.1 절 ACL |
| 로그인 후 바로 로그아웃됨 | 시간이 지나 서버 재기동(세션 메모리) | 다시 로그인(정상). 항상 유지가 필요하면 nginx 인증으로 대체 |
| 한글 파일명 깨짐 | 업로드 시 브라우저 인코딩 | 앱이 파일명을 안전 문자로 치환해 저장(분석 결과 무관) |

진단 묶음:
```bash
systemctl --no-pager status logtriage-server nginx postgresql | head -40
curl -s http://127.0.0.1:8080/healthz; echo
sudo -u postgres psql -qtAc "select count(*) from incidents" logtriage   # PostgreSQL 일 때
tail -n 30 /var/log/logtriage-install.log
```

## 9. 백업·복원
```bash
sudo bash /opt/logtriage/backup.sh                 # → /opt/logtriage/backup/logtriage-backup-<시각>.tar.gz (분석 이력 DB + data/ 의 계정·감시·자산·자동화·게시판 DB + conf/(서버 키) + rules-local + reports), 30일 보관, 파일 권한 600
sudo bash /opt/logtriage/backup.sh --with-env      # 설정(server.env, DB 비밀번호 포함)까지 — 별도 안전 경로에 보관
```
복원:
- **SQLite**: 서비스 중지 → 백업의 `data/` 폴더 전체(분석 이력 `logtriage.db` · 계정 `auth/auth.sqlite3` · 감시 `nms/` · 자산 `inventory/`·`assets/` · 자동화 `automation/` · 게시판 `board/`)를 `/opt/logtriage/data/` 에 덮어쓰고 남은 `*-wal`·`*-shm` 파일은 지움 → 백업의 `conf/secret.key` 를 `/opt/logtriage/conf/` 로(권한 600, 소유자 `logtriage`) → `chown -R logtriage:logtriage /opt/logtriage/data` → 서비스 시작.
- **서버 키(`conf/secret.key`)는 계정 DB 와 짝입니다** — 키 없이 계정 DB 만 옮기면 모든 계정이 로그인할 수 없습니다(22차부터 backup.sh 가 함께 담습니다. 그 전 백업에는 없음).
- **PostgreSQL**: `pg_restore --clean --no-owner --dbname="postgresql://logtriage:<pw>@127.0.0.1:5432/logtriage" logtriage.pgdump`
- `server.env` 는 기본 백업에 없습니다(비밀번호 포함). 재설치 시 install.sh 가 새로 만들며, 기존 DB 를 쓰려면 `LOGTRIAGE_DB` 의 비밀번호를 `ALTER ROLE logtriage PASSWORD ...` 로 맞추거나 `--with-env` 백업본을 복사. `rules-local/` 는 파일 복사.
cron 예: `0 2 * * * root bash /opt/logtriage/backup.sh >> /var/log/logtriage-backup.log 2>&1`

## 10. 보안 체크리스트
- [ ] `LOGTRIAGE_PASSWORD` 를 설치 직후 변경했는가 (`change-me` 금지)
  - 22차부터 서버는 **추측하기 쉬운 공용 비밀번호로 뜨지 않습니다**(nginx 뒤 127.0.0.1 이어도): 예시 값 · 8자 미만 · 숫자만 · 같은 글자 반복 · 흔한 낱말+숫자(`admin2026` · `P@ssw0rd`) · 키보드 연속(`qwerty`).
    설치가 만드는 무작위 12자는 통과합니다. 바꿀 값은 미리 확인(셸 기록에 남지 않게 `read -rs`): `read -rs P; printf '%s\n' "$P" | logtriage-server --check-password --password-stdin; unset P` (0=통과, 2=약함)
  - 사내망도 **HTTPS 로만** 쓰십시오: 평문(HTTP)으로 다른 PC 에서 접속하면 로그인 화면과 앱 위에 경고가 뜹니다. 인증서를 둔 뒤 계정 설정(`conf/auth.json`)의 `require_https` 를 `true` 로 두면 평문 접속을 거절합니다.
  - 앞단 nginx 의 접근 기록에는 1회용 값(에이전트 내려받기 `?ticket=`, 첫 관리자 `/setup?t=`)이 남을 수 있어, 동봉 설정(nginx/logtriage.conf)은 23차부터 `?` 뒤를 적지 않는 `logtriage_noquery` 형식을 씁니다. 직접 만든 nginx 설정이면 `log_format` 에서 `$request` 대신 `$request_method $uri` 를 쓰십시오(앱 자체 기록은 22차부터 가립니다).
  - 로그인 없는(계정 로그인도 공용 비밀번호도 없는) 서버형은 `bash run.sh <포트> local` 처럼 **이 PC 안에서만**이라고 밝힌 기동만 뜹니다(내부적으로 `--local-only`). systemd 정식 설치는 nginx 뒤라 인증 없이는 뜨지 않습니다.
  - 패치(`apply_patch.sh`)는 소스를 바꾸기 **전에** 지금 쓰는 값을 새 규칙으로 진단하고, 걸리면 아무것도 바꾸지 않고 멈춥니다(종료 3) — 값을 바꾼 뒤 다시 실행하십시오.
- [ ] 8080/5432 가 외부에 열려 있지 않은가 (`ss -lntp`)
- [ ] 업로드 로그에 개인정보가 있으면: 파서가 읽는 시점에 주민등록번호 패턴을 마스킹하지만 **원본 파일은 uploads/ 에 남음** → 보관 기간 정책(4.2 절 cron) 적용
- [ ] 룰팩 키(rulepack.key)는 서버에 저장하지 말고 적용 때만 업로드
- [ ] TLS 사용(`--tls` 자체서명은 초기용, 운영은 사내 CA 인증서) · 80→443 리다이렉트 확인
- [ ] 사용자별 인증(nginx auth_basic/SSO) 적용 여부
- [ ] `logtriage-cleanup.timer` 활성(`systemctl list-timers | grep logtriage`)
- [ ] 백업 파일 보관 경로 권한(600) · `--with-env` 백업은 별도 보관
