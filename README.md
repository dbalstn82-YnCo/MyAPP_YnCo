# LogTriage 1.0.0 — 장애 로그 분석 · 1차 대응 지원

> 장애 로그를 넣으면 **원인 후보와 근거 · 역할별 1차 대응 절차 · 공식 서식 보고서**까지 이어 주는 폐쇄망용 도구입니다.
> 운영 중에는 외부 AI 를 쓰지 않고, 규칙과 지식으로 판정합니다 — 같은 로그는 늘 같은 결론입니다.

- 팀: **Team YnCo** · (주)솔리데오 AX 해커톤 2026
- 버전: 1.0.0 (PC · 리눅스 서버 같은 판)
- 이 문서의 숫자는 시험 환경 측정값입니다.

---

## 1. 왜 만들었나

| 업무 | 지금 | LogTriage |
|---|---|---|
| 로그 판독 | 숙련자가 직접 열어 읽음 | 판정 리포트에서 원인 후보 확인 |
| 1차 대응 | 사람마다 다른 판단 | 역할별 확인 절차 · 하면 안 되는 조치 |
| 보고서 | 서식에 손으로 다시 입력 | 공식 서식 자동 작성 · 확인 칸만 입력 |
| 해결 경험 | 담당자 기억에만 | 조치 기록 · 학습 룰로 축적 |
| 환경 | 폐쇄망, 외부 도구 못 씀 | 폐쇄망 그대로 · 외부 AI 없이 |

로그 검색 · 판단 · 보고서 · 기억 사이를 사람이 옮겨 잇던 일을, **원인 판정 → 1차 대응 → 보고서 → 재발 대응**의 한 흐름으로 이었습니다.

## 2. 무엇을 하나

### 분석 엔진
입력 → 제품 판별 → 해석 · 개인정보 가림 → 이벤트 찾기 → 판정 → 대응 계획 · 보고서

| 지원 로그 | 탐지 규칙 | 오류 코드 지식 | 운영 중 외부 AI 호출 |
|---|---|---|---|
| **36종** (제품 30 · 공통 진단 6) | **427개** | **1,605개** (제조사 원인 · 조치 979건 연결) | **0건** |

| 범주 | 제품 |
|---|---|
| OS | Linux · AIX · HP-UX · Solaris · Windows · auditd |
| DB | Oracle · MS-SQL · MySQL · PostgreSQL · Tibero · Altibase · CUBRID · Goldilocks |
| WAS | Tomcat · JEUS · WebLogic · WebSphere · JBoss |
| WEB | Apache · nginx · IIS · WebtoB · 접속 로그 |
| 상용 SW · 공통 | BizMaster · MESIM · Indigo ESB · Java · 계층 공통 |

### 판정 리포트 · 대응 계획
- 결론 한 줄(심각도) · 최초 이상 계층 · 원인 후보 · 판정 요지
- **하면 안 되는 조치**를 먼저 보여 주고, 1차(유지보수) · 2차(엔지니어) · 3차(제조사) 역할별 확인 절차를 제시
- 범주별 시간선(인과 타임라인)과 판정마다 근거 로그 줄

### 보고서 자동 작성
- 공식 서식 2종(상황관리 · 사후관리, 한글 HWPX)의 13 · 23칸을 분석 결과로 자동 기입
- 서식 학습(예전 보고서의 글꼴 · 문단 모양) · 기관 서식 등록(한글 서식의 칸을 분석 값과 연결)
- 모르는 값은 지어내지 않고 **확인 칸**으로 남김

### 쌓이는 대응 자산
- 분석 이력(자동 삭제 없음) · 조치 기록(한 일 · 결과 · 걸린 시간 · 사후 원인) · 현장 지식(승인한 학습 룰) · 자산 대장
- 유사 장애 이력이 있으면 **지난 조치와 결과를 먼저** 보여 줌

### 룰 학습 · 서명 룰팩
- 처음 보는 오류 → 학습 후보 → 초안 · 안전 검증(위험 정규식 · 너무 넓은 룰 · 개인정보 거부) → **관리자 승인** → 다음 분석부터 판정
- 인터넷망 버전에서 키운 지식은 **Ed25519 전자 서명 룰팩**으로 묶어 USB 로 반입 → 폐쇄망에서 키 지문 · 서명 확인 뒤 적용(이전 지식 백업)

### 관제 · 운영
- 실시간 관제(위급한 순서 · 24시간 가용률 · 응답 분포) · 서버 상세(지표 6가지 · 기간별 추이 · 상위 프로세스)
- 에이전트 간편 설치(대상 서버 전용 명령 · 1회용 등록 코드 · 위변조 확인)
- 자산 관리(엑셀 · CSV · 한글 자산 문서 → 장비 대장, 비밀번호 칸은 읽는 즉시 삭제)
- 자동화: 로그 폴더 감시 → 자동 분석 → 보고서 · 게시판 공유 · 알림, 매일 백업 · 정기 점검

## 3. 보안 설계

| 영역 | 지키는 방법 | 막는 것 |
|---|---|---|
| 로그인 | 회사 이메일 · 비밀번호 3중 암호화 · 추측 쉬운 공용 비밀번호 거부 | 비밀번호 유출 · 추측 |
| 부서 경계 | 같은 부서만 원본 공유 · 다른 부서 장비명 가림 | 다른 부서 정보 노출 |
| 자산 | 지정된 사이트 담당자만 조회 | 관리자 권한 남용 |
| 화면 | 허용된 화면 요소만 그림 | 악성 코드 삽입 |
| 반입 | 1회용 등록 코드 · 전자 서명 룰팩만 | 위변조 · 무단 반입 |
| 기록 | 권한 · 설정 · 보고서 정보 변경을 감사 기록에 | 흔적 없는 변경 |

원칙: **보안 때문에 생기는 불편은 감수하고, 안전하게 지킬 수 없는 기능은 두지 않습니다.**

## 4. 설치 방식

|   | 로컬 설치(PC) | 중앙 집중형(서버) | 본사 허브 | 인터넷망 버전 |
|---|---|---|---|---|
| 누가 | 담당자 한 명 | 팀 · 부서 · 관제실 | 본사 운영 | 지식 관리 담당 |
| 설치 | 압축 풀어 바로 실행 | 사내 리눅스 서버에 한 번 | 본사 서버 | 인터넷 PC |
| 로그인 | 없음(이 PC 전용) | 회사 이메일 · 권한 | 회사 이메일 · 권한 | — |
| 자료 | 이 PC 에 저장 | 서버 DB · 부서별 공유 | 요약만 · 원본은 사이트 | 서명 룰팩 → USB |

- **PC**: `LogTriage-PC-1.0.0.zip` 을 풀고 `LogTriage.cmd` 실행(서명된 파이썬 런타임 포함 휴대용 묶음). 실행 기록은 `LogTriage-실행기록.txt` 에 남습니다.
  - exe 판(`-exe.zip`)은 V3 의 '평판 기반 실행 차단'이 켜진 PC 에서 막힐 수 있어 휴대용 묶음을 기본으로 둡니다.
- **서버**: 리눅스(오프라인 설치 묶음) — nginx · LogTriage 서버 · PostgreSQL, systemd 서비스. 절차는 `engine/deploy/server/설치매뉴얼.md` · `LogTriage-설치운영매뉴얼.md`.
- PC 와 리눅스 서버는 같은 코드로 만든 같은 판이며, 매 빌드 21개 항목으로 대조합니다.

## 5. 검증과 수치

| 항목 | 값 | 조건 |
|---|---|---|
| 처리 속도 | 4.8만 줄/초 | 합성 Tomcat 로그 · i5-1235U · 8GB |
| 550MB 로그 분석 | 118초 | 300MB 66초 · 100MB 27초 |
| 작업 메모리 | 64~67MB | 흘려 읽기 · 1회 한도 600MB |
| 자동 시험 | 1,529건 · 실패 0 | 기능 · 권한 · 보안 · 말투 규칙, 매 빌드 |
| 설치본 점검 | 12/12 | 실제 설치 파일을 그대로 실행 |
| PC · 리눅스 같은 판 | 21/21 | 21개 항목 대조 |
| 가상 장애 처리(분석 + 공식 보고서) | 1.6~2.0초 | 가상 장애 3건 · 로그 3~5개 · 제출 PC 묶음 · 3회 가운데 값 |
| 가상 장애 판정 대조(합성 로그) | 장애 5건 중 4건 계층 일치 · 정상 1건 이상 없음 | 틀린 1건(리눅스 OOM 을 OS 로 추정)은 다음 판에서 개선 · 실제 장애 정확도 아님 |

측정값은 시험 환경 기준이며, 로그 종류와 PC 에 따라 달라집니다.

## 6. 만든 방식 — AI 는 개발 동료, 결정은 사람

① 현장 요청(사람) → ② 설계 · 구현(Claude) → ③ 반대 검토(GPT) → ④ 시험 · 화면 확인(Claude) → ⑤ 승인 · 배포(사람)

- 엔진 · 화면 · 시험 · 도구 약 10.5만 줄, GPT 교차 검토 181차(2026-10-28 기준), 개발 55일
- 제품 안의 판정은 규칙과 지식으로 하며, **운영 중 외부 AI 를 호출하지 않습니다.**

## 7. 한계 · 미검증 항목(정직하게 적습니다)

- RHEL 실서버의 에이전트 서비스 설치는 **실기 확인 예정**입니다.
- V3 외 다른 백신 · EDR 과의 호환은 확인하지 않았습니다.
- 업무 시간 절감 효과는 아직 측정하지 않았습니다 — 시범 운영에서 `월 절감 시간 = 월 처리 건수 × (도입 전 − 도입 후 평균 작업 시간)` 으로 실측해 보고합니다.
- 판정은 로그 근거에 따른 **원인 후보**이며, 최종 판단과 조치는 담당자가 합니다.

## 10. 원본에서 실행하기

Python 3.11 이상(시험: 3.11 · 3.13). 저장소를 받은 뒤 `engine` 폴더에서:

```bash
cd engine
pip install -r requirements.txt

# ① PC 화면(Windows · WebView2) — 로그인 없이 이 PC 전용
python run_gui.py

# ② 명령줄 분석
python run_logtriage.py --input samples/nginx_error.log:nginx:web01

# ③ 서버 모드(브라우저 접속) — 이 PC 안에서만 · 첫 관리자는 화면의 안내(1회용 초기 설정 코드)대로 만든다
python -m logtriage.server --host 127.0.0.1 --port 8088 --base ../server-data --local-only
#    → http://127.0.0.1:8088 · 상태 확인: http://127.0.0.1:8088/healthz

# ④ 자동 시험(시험 전용 라이브러리 추가 설치)
pip install -r requirements-dev.txt
PYTHONIOENCODING=utf-8 PYTHONUTF8=1 python -m unittest discover -s tests
```

- 실행 중 만든 분석 이력 · 계정 · 설정은 `engine/data` · `engine/conf` 등(PC 화면) 또는 `--base` 폴더(서버 모드)에 생기며 `.gitignore` 로 저장소에 올라가지 않습니다.
- `run.sh` · `stop.sh` 는 **리눅스 서버 설치 묶음**(독립 실행형 Python 동봉)용 기동 스크립트입니다 — 저장소 원본만으로는 위 ③ 명령을 씁니다.
- 현장 배포는 원본이 아니라 빌드한 묶음(PC 휴대용 ZIP · 리눅스 서버 ZIP)을 씁니다. 빌드 도구(`engine/tools/build/`)는 개발 PC 의 폴더 구성을 전제로 합니다.
